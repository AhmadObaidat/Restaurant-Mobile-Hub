Act as a senior software architect, full-stack engineer, mobile application developer, database engineer, cybersecurity specialist, UI/UX designer, and technical product manager.

Build a production-oriented, scalable software platform for a company that creates and manages independent, branded mobile applications for restaurants and coffee shops.

The initial target market is Jordan, with future expansion into the Gulf Cooperation Council (GCC) countries.

I am the business owner and will manage the platform, restaurant onboarding, application configuration, branding, quality assurance, releases, and publishing processes with my team.

I want to use Replit as my primary AI-assisted development environment. I need you to implement the project in manageable phases, verify each phase, and maintain clear documentation.

Do not merely explain how to build the product. Create the actual application, source code, database schema, migrations, interfaces, backend functionality, tests, and setup instructions.

Do not attempt to implement every feature simultaneously. First establish a reliable foundation, then implement the remaining modules incrementally.

7. MULTI-TENANT DATA ISOLATION

This is a mandatory security requirement.

Every restaurant must operate as an independent tenant within the shared platform.

Every restaurant-owned record must be associated with the appropriate restaurant ID.

The system must prevent one restaurant from accessing another restaurant’s private information.

Examples:

* Restaurant A cannot view Restaurant B’s customers.
* Restaurant A cannot edit Restaurant B’s menu.
* Restaurant A cannot view Restaurant B’s orders.
* Restaurant A cannot view Restaurant B’s sales reports.
* Restaurant A cannot change Restaurant B’s rewards.
* Restaurant A cannot redeem Restaurant B’s reward inventory.
* Restaurant A cannot view Restaurant B’s loyalty transactions.
* Restaurant staff cannot access platform-wide administration.
* Customers cannot view other customers’ private profiles or purchase history.

Implement:

* Server-side authorization.
* Tenant membership validation.
* Role-based access control.
* Database constraints.
* Appropriate row-level security where supported by the database architecture.
* Audit logs for sensitive operations.
* Automated tenant-isolation tests.

Never trust a restaurant ID supplied by the browser without verifying the authenticated user’s access rights.

Never rely solely on hiding interface elements to enforce security.

Use the principle of least privilege.

The platform administrator may access multiple tenants only through explicitly authorized administrative functions.

13. LOYALTY ENGINE

The loyalty engine is a core part of the business.

It must be reusable but configurable independently for every restaurant.

Do not hardcode one reward formula for all restaurants.

Supported Loyalty Program Types

Design the system to support:

1. Points per eligible currency unit spent.
2. Visit-based stamps.
3. Purchase-count rewards.
4. Spending milestones.
5. Tier-based loyalty.
6. Time-limited bonus campaigns.
7. Product-specific bonus points.
8. Birthday rewards.
9. Referral rewards.
10. Custom combinations of supported rules.

Each restaurant can activate one or more compatible program types.

Example: Points Per Purchase

Suppose a restaurant offers 10 points per eligible JOD spent.

A customer makes an eligible purchase of JOD 5.00.

The customer earns 50 points.

Another restaurant may offer 1 point per JOD or a completely different reward model.

These examples are illustrative. All rules must be configurable.

Points Calculation

Use exact monetary representations, such as integer fils, or another carefully defined decimal-safe approach.

Calculate points on the server.

Define how the following affect eligible spending:

* Discounts.
* Taxes.
* Delivery fees.
* Service charges.
* Refunded items.
* Canceled orders.
* Promotional bonuses.

Use a documented default policy and make applicable rules configurable.

Points Ledger

Maintain an immutable transaction ledger containing:

* Restaurant ID.
* Loyalty account ID.
* Transaction type.
* Points earned or spent.
* Related order or redemption.
* Rule version.
* Idempotency key.
* Timestamp.
* Reason or description.

Never let customers directly modify their points balances.

Any corrections must use explicit compensating transactions.

Ensure that the available balance is consistent with the ledger.

Additional Rules

* Award purchase points only after the applicable order reaches the configured qualifying state.
* Do not award points for failed payments.
* Prevent duplicate point awards.
* Reverse eligible points for refunds according to the restaurant’s policy.
* Do not silently delete historical ledger entries.
* Define how points expire.
* Clearly disclose expiration rules.
* Prevent customers from spending more points than they have.
* Prevent concurrent redemptions from overspending the same balance.
* Keep historical transactions understandable after a program’s rules change.

* Canceled.

17. PAYMENT INTEGRATION

Create a provider-independent payment architecture.

The initial launch market is Jordan, so provider selection must be based on actual support for:

* Jordanian merchants.
* JOD transactions.
* Merchant settlement.
* Supported payment methods.
* Refunds.
* Webhooks.
* Transaction reconciliation.
* Required onboarding and compliance procedures.

Research and document candidate providers before implementing a live integration.

Do not assume a provider is available merely because it is popular internationally.

Payment Workflow

1. Customer checks out.
2. Backend validates the cart and order.
3. Backend calculates the final total.
4. Backend creates a pending order.
5. Backend initiates payment through the configured provider.
6. Customer completes the provider’s payment flow.
7. Backend verifies the payment result through a trusted callback or API.
8. Order status is updated.
9. Loyalty points are awarded when the order qualifies.
10. The customer receives confirmation.

Use signed webhook validation, idempotency, and secure provider credentials.

Support payment statuses such as:

* Pending.
* Authorized.
* Paid.
* Failed.
* Canceled.
* Refund pending.
* Partially refunded.
* Refunded.

Do not store raw card details.

Payment Abstraction

Create a consistent internal interface for:

* Creating payment sessions.
* Verifying payment results.
* Processing refund requests.
* Receiving provider webhooks.
* Retrieving transaction status.

The application should not need a complete rewrite when the company adds a different supported payment provider.

Prototype Mode

If provider credentials are unavailable, create a clearly labeled sandbox or simulated payment mode.

Never represent simulated payments as real payments.

18. IN-STORE PURCHASES AND POS INTEGRATION

The platform must support loyalty points for purchases made both through the mobile application and inside the physical restaurant.

Design the architecture for two methods.

Method A: POS Integration

When a supported POS system is available:

1. POS records a completed transaction.
2. The integration securely sends the transaction to the platform.
3. The platform validates the source and transaction identity.
4. The system identifies the eligible customer where possible.
5. The backend calculates qualifying points.
6. The transaction is recorded in the ledger.
7. The customer sees the points in their account.

Support secure webhooks, API authentication, idempotency, and transaction reconciliation.

Do not assume every restaurant’s POS system offers the same API capabilities.

Method B: Staff-Assisted QR or Code Verification

For restaurants without POS integration:

1. Staff creates or verifies a transaction through an authorized interface.
2. The system generates a unique, time-limited transaction token.
3. The customer scans the code or enters the token.
4. The backend verifies the transaction.
5. The points are awarded once.
6. The transaction is recorded.

A customer must never be able to enter any arbitrary spending amount and award themselves points.

Use server-generated transaction records, staff permissions, expiration, and single-use enforcement.

Clearly identify transactions that have not been independently verified.
